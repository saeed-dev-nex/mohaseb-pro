# بررسی خطاهای dialog

از پوشهٔ `frontend`:

```sh
npm run typecheck
npm run build
npm test
```

`dialog-errors.test.mjs` با React server rendering و esbuild موجود، جای پیام
خطا در خود dialog، غیرفعال‌شدن دکمه‌های بستن/انصراف هنگام درخواست و ارتباط
labelهای خدمات را بررسی می‌کند. فقط portal برای SSR جایگزین می‌شود؛ این تست
اجرای واقعی effectها، focus، Escape یا `inert` در مرورگر را تأیید نمی‌کند.
تست‌های callback همان فایل با state قطعی، handlerهای واقعی ذخیره/حذف را
دو بار در یک tick اجرا می‌کنند؛ ارسال تکراری، محل خطا، محدودیت بستن و امکان
تلاش مجدد را می‌سنجند، نه زمان‌بندی React در DOM واقعی.
`api-errors.test.mjs` بدنهٔ خطای Axios/هوک، پیام‌های تودرتو، خطای شبکه و fallback
امن برای پاسخ HTML را می‌سنجد.

## smoke مرورگر بدون دیتابیس و ورود

```sh
node tests/browser-dialog-smoke.mjs
```

صفحهٔ `http://127.0.0.1:4175/dialog-smoke` را باز کنید. harness فقط روی loopback
گوش می‌دهد، API را با دادهٔ ساختگی جایگزین می‌کند و هیچ اطلاعات مشتری یا
درخواستی به backend واقعی نمی‌فرستد. همهٔ ذخیره‌ها/حذف‌ها با دو ثانیه تأخیر
عمداً شکست می‌خورند. اعداد بالای صفحه تعداد فراخوانی‌های mutation هستند.

1. در خدمات «افزودن خدمت» را باز کنید، عنوان را پر کنید و دوبار سریع ذخیره کنید؛
   شمارندهٔ create باید فقط یک واحد زیاد شود.
2. در همان دو ثانیه Escape، دکمهٔ بستن، انصراف و backdrop را امتحان کنید؛ dialog
   نباید بسته شود. پس از شکست، خطا باید داخل dialog و برای screen reader در دسترس باشد.
3. دوباره ذخیره کنید؛ یک درخواست جدید مجاز باشد. پس از پایان، بستن و بازکردن
   مجدد فرم نباید خطای قبلی را نگه دارد.
4. ویرایش و حذف را در هر دو صفحهٔ خدمات و چک‌ها امتحان کنید؛ شکست حذف باید در
   تأییدیهٔ حذف دیده شود، نه پشت آن. فرم چک را برای تست ذخیرهٔ جدید کامل کنید.
5. با Tab به ویرایش/حذف کارت‌ها و ردیف‌ها بروید؛ کنترل دارای focus باید قابل
   دیدن باشد. در عرض کوچک صفحه نیز این کنترل‌ها نباید صرفاً وابسته به hover باشند.
6. پس از بستن dialog، بازگشت focus به کنترل قبلی را بررسی کنید.

با Ctrl+C سرور آزمایشی را متوقف کنید. این harness دستی است، نه E2E خودکار در CI.
